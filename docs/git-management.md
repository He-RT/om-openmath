# Git 管理规则

本文件规定后续开发、提交、集成与发布的做法。2026-10-22 的检查事实、分阶段整改、验证和回退方式见 [Git 整改方案](git-remediation-plan.md)。规则已经写入文档，不表示其中的分支保护、CI 检查或证据迁移已经实施。

当前远程默认分支为 `dev`。保留现有公开历史、发行标签和冻结证据；不为整理历史而强推、移动标签或合并到 `main`。

## 1. 分支与集成

1. `dev` 作为可集成、可回退的基线；新功能、修复和成组维护使用短期任务分支，默认命名为 `codex/<任务>`。从更新后的 `origin/dev` 开始，已有未提交改动先核对归属，不自动清空或覆盖。
2. 在任务分支完成代码和直接相关检查，推送后向 `dev` 提交 PR，写明问题、变更、验证与未覆盖范围。单人项目也进行一次 diff 自审；不要求虚设第二位审批人。
3. 相关检查通过后再集成。CI 失败时优先修复该任务，不能把后续无关功能继续堆入 `dev`；取消、超时、跳过均不算通过。并发设置取消旧运行时，以实际要集成的最新 SHA 为准。
4. 合入时采用仓库允许的普通合并方式，保留可评审的逻辑单元；集成后的最终 SHA 必须有相应验证，不能把 PR 的另一份 SHA 或旧基线结果直接当作发行验证。
5. 已推送的共享分支和公开提交不 rebase、amend 或强推。仅尚未推送的本地提交可整理；已共享的修复追加提交，回退用明确的 revert，不重置公开历史。
6. `main` 不是当前流程的必要条件。新增、切换默认分支或建立另一条发行分支另行决定，不与本次 Git 整理捆绑。

CI 在 `dev` / `main` 的 push 和所有 PR 上始终触发；纯文档也运行轻量检查。`CI required` 按路径分类核对相关任务，失败、取消或意外跳过均不放行；iOS 模拟器仍须显式派发。单独推送任务分支并不等于已经触发 CI。分支保护在远程验证该检查后启用，实际状态与恢复方式见整改方案。

## 2. 提交内容与忽略边界

| 应当提交 | 留在本地或制品存储 |
|---|---|
| 产品源码、测试、必要样例、脚本、平台配置、图标与许可证 | `target/`、依赖安装目录、Web/WASM 编译输出、平台构建缓存 |
| `Cargo.lock`、npm lockfile、Swift `Package.resolved` | 个人 IDE 状态、机器配置、调试日志、完整临时测试根 |
| 约定检查一致性的生成源码、函数文档、原生 Xcode 工程 | Tauri 初始化后由脚本配置的 `app/src-tauri/gen/` |
| 可评审的设计源稿、说明与选定截图 | 设计预览编译出的 `.app`、模块缓存 |
| 必要验收摘要、失败输入、文件清单和 SHA256 | 安装包、签名私钥、含凭据配置、未经筛选的数据库及 blob 存储 |

- [根 `.gitignore`](../.gitignore) 管理默认隔离范围。临时构建、下载、诊断和完整测试输出先落在 `target/<任务>/`，发行包优先放 Release。
- 不使用全局 `*.log`、`*.gz`、`*.obj`、`*.sqlite*`、`*.lock` 代替目录管理。日志可能是失败证据，OBJ 可能是模型数据，数据库和 WAL/SHM 可能是恢复测试输入，依赖锁必须保留。
- `store.lock`、`Blobs/sha256/`、`.xcresult`、`.dSYM` 等按实际用途和目录隔离；不能因名字像运行产物，就把冻结证据或测试样例全局隐藏。
- `.env`、私有签名材料继续忽略；仅提交不含凭据的 `.env.example` 等模板。提交前检查新增配置、日志和附件内容，忽略规则不能代替内容检查。
- 新规则不会自动停止跟踪现有文件。`git ls-files -ci --exclude-standard` 有输出时逐项核对用途，不自动删除，也不用 `git rm -r --cached .` 刷新整个索引。确需取消跟踪时使用审定的精确路径并说明本地保留方式。

## 3. 提交粒度与信息

1. 按明确路径 `git add <路径>`，必要时用 `git add -p`。不使用 `git add .` 或 `git add -A` 无差别收集工作树。
2. 每个提交表达一个可理解、可回退的目的。代码和必要的小样例可一起提交；大量原始证据与代码拆成独立提交，互相注明对应的代码 SHA。拆分不等于丢失失败记录。
3. 暂存区超过 100 个路径，或出现新增大二进制、成批数据库、blob、源码副本时，先逐类核对来源，再决定是否拆分或归档。100 是人工复核触发点，不是允许前 100 个产物入库的额度。
4. 提交首行统一英文 Conventional Commits：`type(scope): subject`，scope 可省略，整行不超过 72 字符，描述完成的具体动作。类型使用 `feat`、`fix`、`build`、`ci`、`docs`、`test`、`perf`、`refactor`、`chore`；工作流修改用 `ci:`。
5. “进行中”、步骤号和计划编号放正文或进度文档；首行不把未接线、未验证的工作写成完成。本地未推送的 WIP 可先留存，推送前整理为可评审单元。
6. 正文或 PR 记录为什么改、验证命令和结果、对应源码 SHA、未验证范围。仅有构建成功不能写成实际安装、设备运行或全部功能通过。

提交前至少检查：

```sh
git status --short
git diff --cached --stat
git diff --cached
git diff --cached --check
git ls-files -ci --exclude-standard
```

## 4. CI 与跳过检查

- 默认运行 CI。源码、测试、依赖与锁文件、构建脚本、平台配置及 `.github/workflows/` 的变更不得使用 `[skip ci]` 等跳过标记。
- 纯说明文档或忽略/属性规则整理，可在确认不影响构建、发布和检查语义后使用跳过标记，并记录已经做过的轻量验证。涉及可执行代码的设计稿也按实际内容判断，不能只因位于 `docs/` 就跳过。
- 优先使用工作流已有的路径判断，不重复添加跳过标记。当前 [ci.yml](../.github/workflows/ci.yml) 只排除 `docs/plan/**`、`docs/acceptance/**`、`docs/README.md` 和 `CODEX_HANDOFF.md`；本文件和一般设计文档不在该名单中。
- “未触发”“skipped”“cancelled”“failure”分别如实记录，均不得记为绿色通过。`workflow_dispatch` 不受提交信息的跳过标记阻止，但一次手动打包成功只证明它实际覆盖的检查，不能替代未运行的依赖、Rust 或前端检查。
- 检查结果绑定完整 SHA、workflow、run URL 和范围；产品源码与打包脚本分开检出时，两者 SHA 都要记录。后续又改了任一输入，重新检查受影响部分。
- 功能进入 `dev` 前通过相关检查；发行前确认最终输入有完整的适用检查。iOS、真机、真实模型等按本轮明确范围运行，未运行项保留为未覆盖，不为文档修改重复旧全矩阵或收费模型调用。
- 不用“连续跳过几次后再补测”代替门槛。CI 应在集成点约束相关代码；纯文档提交也不因计数达到阈值就重跑全部产品验收。

启用 required checks 前，要让文档 PR 也能获得明确的检查结果。避免把会被整个 workflow 的 `paths-ignore` 跳过的检查直接设为必需，否则 PR 可能一直等待；具体改造列入整改方案。

## 5. 验收证据与 `.gitattributes`

1. 从临时根挑选能支撑结论的摘要、关键日志、截图、必要失败输入及散列清单进入 `docs/acceptance/`。不把完整运行根、依赖缓存、数据库、blob 存储或重复源码快照展开成成千上万个路径。
2. 需要保留完整原始根时，使用单个归档及 SHA256、逐文件清单，或放入 Release 等持久制品存储。记录代码 SHA、运行入口、工具版本、成功与失败范围，以及恢复/校验方法；不能只依赖会过期的 Actions artifact 链接。
3. 已冻结证据保持字节和散列。历史日志中的本机路径、失败状态和原始输出不做批量清洗。旧证据迁移必须按整改方案完成清单、下载、解包和引用校验后再移出当前树。
4. [`.gitattributes`](../.gitattributes) 的许可证、日志、SSE、二进制例外按已知用途设置。SSE 保留末尾空行要求；不把整个验收目录设为 `binary` 或关闭全部 whitespace 检查。
5. 合并重复属性规则前，对已有路径逐项比较 `git check-attr` 结果，审阅新增匹配范围。不要为缩短规则而扩大例外，也不对冻结档案执行 `git add --renormalize`。
6. 移出当前树可以减少索引、检出和搜索路径；保留历史时，旧 blob 仍可达，普通完整 clone 的历史体积不会因此显著缩小。不要把这类迁移称为历史瘦身。

## 6. 文档和脚本的可移植性

- 新的操作说明使用仓库相对路径，必要时定义 `$REPO` 等变量。可执行脚本与测试使用配置或临时目录，不依赖个人用户名和固定安装位置。
- 旧文档区分“当前操作入口”和“当时验收事实”：前者逐项改为可移植路径，后者保留历史语义。测试中的固定路径先判断用途，不能机械替换后破坏断言。
- 搜索本机路径只是发现线索；检索规则本身、历史证据和有意测试样例可以出现路径文本。发布前逐项审查命中，不以一次粗略搜索的空结果代替验证。

## 7. 标签、发行与补包

1. 新发行使用附注标签，例如 `git tag -a <新版本标签> <已验证SHA> -m "<发行说明>"`。有合适签名身份时可使用签名标签；已有轻量标签仍是有效定位点，保持不动。
2. 标签打在通过适用检查的确定提交上。发布前核对版本、锁文件、生成文件、包内 revision、资产大小及 SHA256，保存对应 Actions run 和已覆盖平台。
3. 一次发行用冻结清单记录全部输入：产品源码 SHA、各平台打包脚本/工作流 SHA、构建参数、工具链/依赖版本、run URL，以及每个资产的文件名、大小和 SHA256。多个来源提交可以复现，但不能声称只检出产品标签就能复现所有补包。
4. 清单里的输入必须能取回。现有 [release.py](../scripts/release.py) 及各份 manifest 已覆盖部分字段；尚缺的统一来源与 run 信息按整改方案补齐，不把文档要求当成现有自动能力。
5. 已发布标签不移动、不删除；已公开同名资产不覆盖。产品变化用新版本；纯平台补包如沿用原 Release，使用新增资产/补充清单明确对应原资产及其输入，保留原清单和字节，不伪装成原标签构建。
6. 发布内容与验证覆盖分开记录。构建产物安装、公开下载校验、设备/模拟器运行分别记录，不能相互替代。

## 8. 日常操作顺序

开始任务时核对工作树、分支和上游，在短期分支实现；提交前审阅精确暂存内容；推送并创建 PR，等待相关检查；检查通过后集成，再以最终输入准备发行。仅获授权写文档或提出方案时，交付文档与验证结果，不自动提交、推送或执行方案。

每次发行前额外审查已跟踪但命中忽略规则的路径、最大的新增 blob、非证据区本机路径、最终 SHA 的 CI，以及发行清单的来源和散列。检查应针对本次输入，不机械重复已冻结且未变化的历史验收。
