## 2. 需要解决的具体问题

- **集成缺少门槛。** 任务直接推进 `dev`，期间存在连续失败的 CI。例如 [39171752426](https://github.com/He-RT/om-openmath/actions/runs/39171752426) 的依赖检查与 Rust lint 失败；[39311646746](https://github.com/He-RT/om-openmath/actions/runs/39311646746) 还包含前端测试失败，不能都归为取消或环境噪声。后续 [39488786752](https://github.com/He-RT/om-openmath/actions/runs/39488786752) 已通过适用的常规检查，说明问题后来修复，不代表前面的提交均可回退即用。
- **代码被大量证据淹没。** `28f85704` 修改 7,879 个路径，其中 7,831 个属于验收目录；`efb36c1e` 为 5,744 / 5,681，`27dd0e91` 为 2,819 / 2,799。单个逻辑改动难以评审、选择性回退。
- **检查范围不易从历史看清。** 多个打包/脚本提交跳过常规 CI，但另有手动打包与安装检查，例如 [Windows 39635714219](https://github.com/He-RT/om-openmath/actions/runs/39635714219) 和 [Android 39644931736](https://github.com/He-RT/om-openmath/actions/runs/39644931736)。应记录各自覆盖，不能简单写成“完全没测试”或“全部 CI 已通过”。
- **发行输入分散。** `.5` 的产品标签指向 `86da0620`，Tauri 补包产品源码为 `29481853`，Windows/Android 打包来源又不同。已有 [补包记录](acceptance/pre-alpha.5/tauri-release.md) 与清单披露这些事实；仍需统一索引完整输入，降低复现成本。
- **维护规则可以更精确。** 子目录 IDE 状态、npm 调试输出、临时原生结果的隔离仍可检查；`.gitattributes` 的重复路径规则可审慎收敛；操作说明中的本机路径影响复用。不能因此全局忽略日志/数据库，或批量改动历史证据。

### R2：让短期分支、CI 和集成门槛生效

状态：完成。PR #2 常规 CI 通过后集成，`dev` 已启用 PR/`CI required`/strict/管理员约束和禁止强推、删除；所需审批数为 0。PR #4 失败时服务器拒绝合并；修复后的最新检查作为该文档的集成门槛。前值、实际结果及维护恢复见 [执行结果](git-remediation-results.md#r2cipr-与-dev-保护)。

1. 保留 `dev` 为默认集成分支；新任务从 `origin/dev` 建短期分支，经 PR 进入 `dev`。不要求新增 `main`，不改变已有发布分支或标签。
2. 给集成建立始终能报告结果的检查入口。路径分类决定运行哪些任务，但整个 required workflow 不能因 `paths-ignore` 消失；文档/规则变更也有明确的轻量检查和汇总结果。
3. 汇总检查应按变更类型确认预期任务确实运行并成功；只允许有依据的非适用任务跳过。失败、意外跳过和取消不能因聚合 job 自身退出成功而放行。
4. 常规源码/脚本/依赖/工作流提交去掉跳过 CI 的习惯；发布工作流仍用于平台特定构建与安装验证，并记录产品和工作流实际 SHA。对变更运行有意义的相关检查，不为规则文档重跑全部发行和模型矩阵。
5. 在短期分支的 PR 上验证至少三种情形：纯文档获得结果；代码修改运行相关检查；相关任务失败会让汇总检查失败。修改 CI 本身要经正常 CI，不能写 `[skip ci]`。
6. 验证通过并确定检查名称后，再为 `dev` 启用 PR/required checks、禁止强推与删除的保护；使用 GitHub 实际支持的 protection 或 ruleset。启用后用实际 PR 验证失败会阻止合并、纯文档检查通过后可以合并。单人维护不强设第二人审批；保留明确的维护恢复方式，不能把自己永久锁在无结果的检查外。

完成标准：一条实际 PR 展示检查与集成路径，失败与纯文档情形有可检查结果；远程规则与文档一致；最终集成 SHA 的检查范围明确。实施时记录检查名称、配置和变更前值，不能先宣称分支已受保护。

回退：保留配置前值，必要时恢复规则；CI 修复用追加提交。不能用恢复直推或跳过失败检查掩盖产品问题。

### R4：评估并迁移 `r43` 的完整原始根

状态：待选择执行；涉及新增外部资产及从后续提交移除目录，执行范围须单独明确。它不是解决 CI 门槛的前置条件。

1. **先盘点，后确定清单。** 以届时确定的代码 SHA 枚举 `docs/acceptance/pre-alpha.4/development/r43/`，列明要迁移的原始目录、留仓结论/摘要/清单、直接引用它们的文档和脚本。不使用未经审阅的 `*-raw` 通配直接取消跟踪；大型 JSON 也按用途判断。
2. **构建可校验归档。** 在 `target/<任务>/` 创建一个原始根归档，例如 `r43-raw.tar.zst`，连同逐文件路径、类型、大小、内容 SHA256、可执行位和符号链接目标清单，以及归档自身 SHA256。只从固定提交/核实副本取材，不混入后来运行状态。保留原有内部散列清单；先检查打包和解包所需空间。
3. **本地解包验证。** 对比路径集合、类型、权限/链接和每个文件散列；识别重复名、路径穿越和指向归档外的链接。原清单使用相对路径校验时，从对应根运行。验证所有文件，不只比较压缩包 SHA。
4. **先上传并验证可取回。** 将归档及清单放入选定的持久位置；可为 `.4` Release 新增独立命名的证据附件，不覆盖旧资产或改 tag。下载上传后的实际附件，再完整解包核对一次，保存 URL、大小、SHA256 和恢复步骤。
5. **先修引用，再移出当前树。** 仓库保留 README/索引、结论、必要摘要与下载/恢复说明。直接依赖原始路径的脚本改为显式恢复步骤，并验证相关读取/恢复流程。外部文件可取回、逐文件核对和引用修复都通过后，才在独立提交中移除审定目录；若要求本地保留，用明确路径取消跟踪并设置精确本地隔离规则，提前说明其他使用者拉取提交时的删除影响。
6. **最后复核。** 比较整改前后跟踪路径数量、保留结论和散列，检查所有链接与脚本入口。保留旧 commit/tag 与迁移前可恢复副本，完成后再决定临时副本如何清理；不自动删除本地原始数据。

完成标准：有固定来源、可取回归档、逐文件一致性、可运行恢复说明和没有悬空引用的后续树；旧 tag 与原始字节不变。收益是减少当前检出/索引/搜索的路径，**不是缩小已存在的 Git 历史**；新克隆仍会下载可达旧对象，除非使用另行约定的 shallow/partial clone。

回退：移除提交可用 revert 恢复；归档和来源 SHA 继续保留。远程下载、散列或恢复核验任一步失败，都不进入移除阶段。
